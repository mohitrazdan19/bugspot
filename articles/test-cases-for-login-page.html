40 test cases for a login page (functional, negative, security and UI)

“Write test cases for a login page” is the most asked practical question in QA interviews. Here are 40 test cases, grouped the way an experienced tester thinks about them.

A login page has two fields and one button, which is exactly why interviewers love it. Anyone can list five test cases. A good tester lists forty, because they think about the data, the server, the attacker, the slow network and the person using a screen reader, not just the happy path.

Use this list as a checklist at work, or learn the groups for your next interview. Each test case has an expected result, because a test case without one is just an idea.

Positive test cases

These check that the login works for a real user doing the right thing.

#Test caseExpected result
1Log in with a valid username and valid passwordUser lands on the home or dashboard page, signed in
2Log in with a registered email instead of a username (if allowed)Login succeeds
3Log in with a registered mobile number and correct OTPLogin succeeds
4Press Enter in the password field instead of clicking LoginForm submits, same as clicking Login
5Tick “Remember me”, log in, close and reopen the browserUser is still signed in
6Log in, then click LogoutSession ends; the back button does not show the signed-in page
7Email with capital letters (Riya@Mail.com) for an account saved in lower caseLogin succeeds, emails are compared without case
8Email with a space before or after itSpaces are trimmed and login succeeds

Cases 7 and 8 look small, but they hide real database bugs. If an email was saved with a trailing space, that user may never be able to sign in.

Security test cases

This is the group that separates freshers from experienced testers in an interview. Even if you are not a security tester, you should check these.

20Type in the password fieldCharacters are masked; the show/hide eye icon works both ways

22Enter a wrong password 5 timesAccount is locked for a while or a CAPTCHA appears

How to answer this in an interview

Do not read out forty cases. Interviewers want to see how you think. Say the groups first: “I would cover positive cases, negative cases, security, UI and accessibility, and performance.” Then give two or three strong examples from each group, and finish with one case most people forget, such as the same OTP working twice or the old session staying alive after a password change. If they ask for the format, use the columns from our guide on how to write a test case.

Frequently asked questions

How many test cases can you write for a login page?

Easily 40 or more when you include positive, negative, security, UI, accessibility, performance and compatibility checks. In an interview, name the groups and give a few strong examples from each.

What are negative test cases for a login page?

Wrong password, unregistered user, empty fields, invalid email format, password in the wrong case, very long input, a deleted account and wrong, expired or reused OTPs.

What security test cases should a login page have?

Password masking, https with POST, no password in the URL, account lock after repeated failures, SQL injection and script injection checks, no stack traces in errors, and old sessions ending after a password change.

Should the error message say whether the username or the password is wrong?

No. A general message such as “Email or password is incorrect” stops attackers from finding out which accounts exist.
