How to write a test case, with format and examples

A test case is a small, repeatable experiment: do these steps with this data, and expect this result. Here is the standard format, a worked example and the habits that make test cases useful.

Many new testers think test cases are paperwork. They are not. A good test case is what lets anyone on the team, on any day, check the same thing the same way and get a clear pass or fail. It is also how you prove what was tested when a bug reaches production.

What is a test case?

A test case is a set of steps, test data and an expected result that checks one specific thing in the product. If the actual result matches the expected result, the test passes. If not, you have found a bug and you write a bug report.

Three related words get mixed up in interviews:

  • Test scenario: what to test, in one line. “Check that the cart total is correct.”
  • Test case: how to test it, with steps, data and an expected result. One scenario usually has several test cases.
  • Test script: an automated version of a test case, written in code (Selenium, Playwright, Cypress and so on).

The standard test case format

Teams use Excel, Google Sheets, TestRail, Zephyr or Xray, but the columns are almost always these:

FieldWhat to write
Test case IDA unique ID such as TC_CART_001
TitleWhat this case checks, in one line
Module / requirementThe feature or user story it covers, for traceability
PreconditionsWhat must be true before step 1
Test dataThe exact values to use
StepsNumbered actions, one per step
Expected resultWhat should happen, stated so that pass or fail is obvious
Actual resultFilled in during execution
StatusPass, Fail, Blocked or Not run
PriorityHigh, Medium or Low, so the most important cases run first

A worked example: the cart total

Requirement: “The order total is the sum of all items, plus delivery, minus discounts.” Here is one test case for it.

IDTC_CART_004
TitleOrder total equals items plus delivery
PreconditionsUser signed in, cart empty, delivery fee for this pin code is ₹40
Test dataItem A ₹525 × 1, Item B ₹300 × 2
Steps1. Add Item A with quantity 1.
2. Add Item B with quantity 2.
3. Open the cart.
4. Read the price summary.
ExpectedItems ₹1,125, Delivery ₹40, Total ₹1,165
PriorityHigh

Where test cases come from

You do not have to invent test cases from nothing. Four simple techniques produce most of them:

  • Equivalence partitioning: split inputs into groups that should behave the same, and test one value from each. For an age field that accepts 18 to 60: one value below 18, one between, one above.
  • Boundary value analysis: bugs live at the edges, so test 17, 18, 60 and 61, not just 30.
  • Decision tables: list combinations of conditions, such as coupon valid or expired and cart above or below ₹499, and write a case for each row.
  • Error guessing: use experience. Negative quantity, 31 February, a leap year, an emoji in a name, a double click on Pay.

The rule behind every row: someone else should be able to run your test case without asking you anything, and agree with you on pass or fail.

Tips that make test cases last

  • Write for a new joiner. If they could not run it on their first day, add detail.
  • Keep each case independent. A case should not depend on the previous one having passed.
  • Link to the requirement. A traceability matrix (requirement → test cases) shows nothing was missed.
  • Cover negative paths. Most real bugs are in what the user should not be able to do.
  • Review and update. When the product changes, outdated test cases cause false failures and lost trust.
  • Do the maths yourself. Totals, taxes, percentages and dates should be calculated in your expected result.

Frequently asked questions

What is the format of a test case?

Test case ID, title, module or requirement, preconditions, test data, steps, expected result, actual result, status and priority.

What is the difference between a test case and a test scenario?

A test scenario says what to test in one line, such as “check the cart total”. A test case says exactly how, with steps, data and an expected result. One scenario usually has several test cases.

How many test cases should one feature have?

There is no fixed number. Cover each requirement with positive cases, negative cases and boundary values. A simple form can need 20 to 40 cases.

Which tools are used to write test cases?

Excel or Google Sheets for small teams, and TestRail, Zephyr, Xray or Azure Test Plans in larger companies.
