Bug life cycle (defect life cycle) explained with every status

Every bug goes on a journey from the moment a tester finds it to the moment it is closed. This guide walks through each status, who owns it and the questions interviewers ask about it.

The bug life cycle, also called the defect life cycle, is the set of statuses a bug moves through in a tracker such as Jira, from New to Closed. Knowing it helps you in two ways: at work you always know whose turn it is, and in interviews it is one of the most asked manual testing questions.

The main flow at a glance

Most bugs follow this happy path:

New → Assigned → Open → Fixed → Retest → Verified → Closed

Some bugs leave the path: they are rejected, deferred, marked duplicate, or fail retest and go back as Reopened. Tools and companies use slightly different names (for example “In Progress” instead of Open, or “Ready for QA” instead of Retest), but the idea is the same.

Every status, one by one

StatusWhat it meansWho moves it
NewThe tester has logged the bug. Nobody has reviewed it yet.Tester
AssignedThe lead or triage team has accepted it and given it to a developer.Test lead, dev lead or product owner
Open / In progressThe developer is analysing and fixing it.Developer
FixedThe code change is done and merged.Developer
Retest / Ready for QAThe fix is deployed to the test environment and waiting for the tester.Developer or build team
VerifiedThe tester followed the steps again and the bug is gone.Tester
ClosedVerified and no further work is needed. The bug’s life is over.Tester or lead
ReopenedThe bug is still there after the fix, or came back later.Tester

The side paths: Rejected, Duplicate, Deferred, Not a bug

  • Rejected / Not a bug: the developer or lead believes the behaviour is correct. Often this means the requirement was unclear. Do not argue in comments; point to the requirement, or ask the product owner to decide.
  • Duplicate: the same bug is already logged. Link the two tickets and close the new one. Searching the tracker before you log a bug avoids this.
  • Deferred / Postponed: it is a real bug, but it will be fixed in a later release. This is a priority decision, usually for low-impact bugs close to a release date.
  • Cannot reproduce: the developer could not see the bug with the steps given. The fix is almost always a better bug report: exact data, environment, build number and a screen recording.

A typo on the home page might be deferred in one team and fixed the same day in another. That is the difference between severity and priority.

Retesting a fix the right way

When a bug comes back as Retest, do three things before you mark it Verified:

  1. Repeat the exact steps from the report, with the same data.
  2. Try the nearby values. If the bug was a wrong discount on ₹1,200, also try ₹999 and ₹10,000. Fixes are often too narrow.
  3. Run a quick regression of the screens around the fix, because a fix in one place can break another.

If any of these fail, move the bug to Reopened with a comment saying which build you tested and what you saw.

Why bugs get reopened

A high reopen count is a warning sign for a team. The common causes are:

  • The fix covered one case but not the general rule (fixed for one coupon, not all coupons).
  • The fix was not deployed to the environment the tester was using.
  • The original report was vague, so the developer fixed a different problem.
  • Caching: the old value is still being served. Clear the cache or check the API directly.

Interview questions on the bug life cycle

Q: Explain the bug life cycle. Draw or list the main flow, New to Closed, then mention the side paths: Rejected, Duplicate, Deferred and Reopened. Say who owns each step.

Q: What do you do if a developer rejects your bug? Re-check the requirement and reproduce it once more. If you still believe it is a bug, add evidence and ask the product owner or lead to decide. Stay factual and polite.

Q: What is the difference between Deferred and Rejected? Deferred means it is a real bug that will be fixed later. Rejected means the team decided it is not a bug.

Q: Can a tester close a bug? Yes, in most teams the tester closes the bug after verifying the fix. Some teams leave the final close to the lead.

Frequently asked questions

What is the bug life cycle in software testing?

It is the set of statuses a bug moves through, from New to Closed: New, Assigned, Open, Fixed, Retest, Verified and Closed, with side paths such as Rejected, Duplicate, Deferred and Reopened.

Is the bug life cycle the same as the defect life cycle?

Yes. The two names are used for the same thing.

When is a bug reopened?

When the tester retests the fix and the bug is still there, or when the same bug comes back in a later build.

What is the difference between Deferred and Rejected?

Deferred means it is a real bug that will be fixed in a later release. Rejected means the team decided the behaviour is correct, so it is not a bug.

Who closes a bug?

Usually the tester, after verifying the fix in the test environment. Some teams let the test lead do the final close.
